# Lesson 10: Steerability

Course: AI Capabilities and Limitations (Claude Academy) Section: Steerability (lesson 10 of 13, about 25 min) Type: Short video/summary (5 min) + one exercise ("The Goal Rewrite")

Note: the example task and ideas in section 4 are my own suggestions, tied to my AI security goal. The lesson itself is generic.

# Learning goals
Explain why steerability works (fine-tuning taught the model to follow instructions) and why it has limits (instructions are followed by pattern-matching, not understanding)
Predict where control is tightest (short, concrete, verifiable instructions) and loosest (long reasoning chains, abstract asks, native precision tasks)
Identify the failures: reasoning drift, letter-over-spirit, brittle arithmetic
Recognize system prompts, code execution, visible reasoning, and structured outputs as product features that address this limit

# 1. Core idea

The model follows my instructions the same way it does everything else: by continuing a pattern (Next Token Prediction). That makes it very steerable. It also means there is always a gap between what I intended and what landed, and most interesting failures live in that gap.

# 2. Two zones
**Capability zone** (tight control)                  	**Limitation zone** (loose control)
Short, concrete, verifiable instructions	       Long chains of reasoning
Format specs, length limits, explicit roles	     Abstract or ambiguous instructions
	Anything needing native numerical or logical precision

# 3. Characteristic failures
Failure	                             What it looks like
**Reasoning drift**	             Small errors early on compound through the later steps
**Letter-over-spirit**	         The instruction is honored but my intent isn't
**Brittle arithmetic**	         Math or exact logic done "by pattern" goes wrong

The fixes: system prompts, code execution, visible reasoning, and structured output modes keep my intent from diluting.

**Key rule**: when an instruction is followed literally but uselessly, restate the goal. Repeating the instruction with more force won't close the gap.

4D link: Steerability is what makes Description powerful and what bounds it. Understanding the gap between words and intent changes how I write prompts and where I add checkpoints.

# 4. Exercise: The Goal Rewrite

**Why**: The gap between what I say and what I mean is where most steerability failures live. This teaches me to prompt from intent, not just instruction.

Setup: Pick a multi-step or format-specific task from my Lesson 1 list. Write the goal in one sentence: what I'm actually trying to accomplish, not just how the output looks.

Goal example from the lesson: "Convince my team this timeline is realistic."
Format example: "Three bullet points."

My idea (to check and edit): the LinkedIn "About" section from my career-switch project. Goal: "Make a recruiter in AI security see me as a serious career-switcher with real, transferable skills." (Format would be "150 words, first person.")

Three probes
**Tight control**: Give a short, concrete, verifiable instruction ("a three-column table", "exactly five bullet points", "second person throughout"). Check that it held precisely. This is the capability zone.
**Reasoning drift**: Ask for a version of the task with 4-5 dependent steps. Check each step: did an early error carry through? Then retry, asking the AI to stop and show step 2 before continuing. Compare running straight through vs. using a checkpoint.
**Letter vs. spirit**: Give an instruction that can be satisfied literally but uselessly (e.g., "Make this shorter" when the real problem is structure; "Make this more professional" when the email buries the ask). See the result. Then re-prompt with the goal stated next to the instruction, e.g. "Make this shorter. My goal is to keep the executive's attention through the key finding on page two." Compare.

Annotate the task list:

For multi-step tasks, note where I'd insert a checkpoint.
For tasks where I've prompted with format alone, draft the goal statement to add next time.

# 5. Reflection questions (answer in my own words)
How often have I stated format but not goal? What changes when I include both?
What is one recurring task where I'll add a mid-process checkpoint starting this week?

# Quick revision
Steerability = instruction-following via pattern continuation, not understanding.
Tight control: short, concrete, verifiable. Loose control: long reasoning, abstract asks, precise math.
Failures: reasoning drift, letter-over-spirit, brittle arithmetic.
Fix drift with checkpoints. Fix letter-over-spirit by stating the goal.
Product help: system prompts, code execution, visible reasoning, structured outputs.
Don't just repeat the instruction louder. Restate the goal.

# Link to AI Security (my goal)
Instructions are patterns, not rules: a model can be steered by any instruction in its context, including a hidden one in a document. This is the core reason prompt injection works (my story idea "The assistant that got tricked").
Letter-over-spirit is a safety issue too: an AI may follow the wording of a safety rule while missing its intent. Good guardrails need goals, plus checks outside the model.
Checkpoints = human-in-the-loop control. They match the "How I'll check it" column in my delegation plan (Discernment).
Brittle arithmetic: don't trust calculations (risk scores, counts) without code execution or my own check.
System prompts set the standing rules, but they are not a security boundary by themselves.
